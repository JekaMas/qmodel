### IR-002 — Medium — Explicit fresh verification can reuse a prior replay instead of executing a checker

Classification: demonstrated harness defect. Requirement: task-v2 §6 lines 165–175, §7 line 186 and §8 lines 227–236; repository documentation promises that `--fresh` reruns the exact saved inputs.

Baseline `scripts/verify.py:28–31` invokes `replay.py`; `replay.py:34` calls `evidence.execute`; `evidence.py:23–28` returns an existing successful receipt whenever command and input hashes match. Consequently an already replayed observation can print `REUSE` without starting the checker, even when requested through `--fresh`. The final mode still says `exact-recorded-input rerun`. Also `replay.latest` filters out failed/timeout attempts and treats an exact base ID as a family lookup, so the documented reproduction route cannot select every original failed attempt unambiguously.

Minimal repair: add an explicit forced-execution path for fresh/replay requests, use unique attempt outputs, and distinguish exact receipt selection from an explicitly requested latest-success selection. Permit exact original timeout/tool-error reproduction while retaining its expected non-success classification and limits. Test that a checker subprocess actually executes on two consecutive forced calls and that exact failed attempt selection does not silently pick a later success.

Invalidated claims: fresh-execution/replay provenance for invocations that returned cached replay receipts, plus universal exact-attempt reproduction documentation. Original native results and their saved source closures remain valid; this does not invalidate economic model properties.

Status: RESOLVED after immutable trace association, forced exact execution and explicit historical reproduction availability; see final recheck below.

### IR-003 — High — The evidence audit does not bind a native observation to the intended proof contract

Validate consistency between native summary, process exit and recorded outcome. Preserve original native output and source identity rather than silently rehashing it to grant a new claim. Add discriminators for changed claim/command, unrelated violation, raw corruption, source corruption, zero-selected scenarios and tool errors.

Invalidated claims: strength of the evidence-audit guarantee and any completion gate relying solely on that acceptance mechanism. This is not evidence that the original native logs were fabricated or that their actual economic properties fail. Those logs retain their original narrower observation boundary.

Status: RESOLVED after source recheck, rejection of the original discriminator and readback of all 14 passing audit tests.

The separate `models/capacity.qnt:6–12` has a finite hostile-work budget and FIFO service, with no recovery-priority rule. The precise 14/22/24 slot calculation is therefore a two-trade bounded round-robin result, not a bound under the additional hostile-work/priority scenario described in that paragraph.

Minimal repair: make the resource statement match each actual configuration. Preserve the two-trade 14/22/24 result with its current assumptions, and separately exercise a queue configuration that admits bounded hostile work and explicitly distinguishes the recovery scheduling policy if claiming that priority behavior. FIFO plus a finite hostile budget can also be reported honestly as a different scoped scheduling result. Record unchecked combined deadline/hostile/recovery interactions.

Invalidated claims: only the extra timed hostile-work/recovery-priority scope. Existing two-trade timed bounds, exact margin controls and separate capacity safety/progress results are not invalidated by correcting the prose. A changed timed scheduler/workload invalidates its affected timing results and needs new names/receipts.

Status: RESOLVED by exact configuration prose and actual FIFO workload witnesses; original timing results retain their existing proof boundary.
