## Findings, in priority order

### QA-01 — P-Binding omits identity, account and other returned values (high)

Location: [privacy_pipeline.qnt](../../models/privacy_pipeline.qnt#L155), `disclosureBound`, lines 155–162; `fieldValue` lines 88–96; `PBinding` line 168. This concerns task v2 P-Binding, line 294, and the description in [privacy-policy.md](../../privacy-policy.md#L49).

The payload constructor returns actual field values, but its binding oracle checks `value` only for fields 2, 3, 6 and 7. Other field values fall through to true. A returned identity can therefore name the other valid account while the source snapshot, evidence, access policy and oracle provenance remain unchanged. PAccess and paired public observations do not catch this: an authorized private disclosure can carry an incorrect value without leaking it publicly.

**Observed discriminator:** a copied constructor corrupts exactly one field after its source lookup. For identity (field 0), actual recipient 1 is replaced by valid account 0; for account (field 1), actual sender 0 is replaced by valid account 1. Both still satisfy PBinding, PAccess, PNI and PTiming. All 16 field discriminators executed: the oracle detects wrong values for 2/3/6/7 and misses them for 0/1/4/5/8/9/10/11/12/13/14/15. The checks explicitly assert this result; their passing test status means the discriminator worked, not that incorrect disclosure is safe. See [field results](review.json) and `evidence/observations/runs/privacy-value-*/`.

**Required repair:** independently compare each successful payload field with its captured transition and applicable public context, including identities/accounts, eligibility, program, root, trade, outcome and routing. Check status/redaction separately. Retain per-field wrong-value controls and exact-value positive cases. Do not repair by calling the same mutable payload constructor from the oracle. Rerun affected payload/access/binding checks and the timed privacy product; unrelated financial graphs remain reusable.

### QA-02 — Program-admission rejection is not exercised at the proof consumer (medium)

Location: [dvp.qnt](../../models/dvp.qnt#L30), `fact` line 30, `authFact` lines 55–58, `prove` lines 113–114, `inject` lines 121–134, `canCommit` lines 139–145; [bindings_test.qnt](../../tests/bindings_test.qnt#L4), lines 4–25. This concerns S10 and the changed-version input required by task v2 lines 73 and 133.

Every legitimately produced core fact uses program 1, and the core retains program 1. Injection can change the program, but the changed whole Fact is absent from `proofs`; it is already rejected by provenance membership. The 22 descriptor-binding cases call `requestOpen`, not the proof consumer. Focused membership checks do test retained manifests and retired credentials; they do not connect an otherwise proven unadmitted program to the financial proof consumer.

**Observed discriminator:** omit only program admission at the COMMIT consumer, preserving every other proof condition and leaving strict `authFact`/S10 unchanged. Canonical-program settlement and all 22 copied descriptor-binding tests still pass. Supply an otherwise proven fact produced under program 2, with history still admitting only 1: the original consumer rejects COMMIT, while the weakened consumer commits and the unchanged S10 produces a native counterexample. This explicitly extends the producer input domain; it is not a reachable attack on the unchanged model. See `program_weak_canonical`, `program_weak_bindings`, `program_strict_foreign-attempt1`, and [the native S10 trace](evidence/observations/runs/program-weak-foreign-S10/native.itf.json).

**Required repair:** separate cryptographic/provenance validity from application admission. Add finite authentic foreign/unadmitted program contexts and verify them through the real consumer path. Include a missing-program-admission mutant that the extended suite kills, with strict matching/admission assertions unchanged. Apply the same masking audit to checkpoint, domain, root and configuration substitutions. Existing `authentication.qnt` checkpoint/history controls remain useful; they do not discharge all core version bindings.

### QA-03 — ABORT reconciliation lacks an independent resolved-obligation assertion (medium)

Location: [dvp.qnt](../../models/dvp.qnt#L231), `captureAbortRecord` lines 231–238, `hasAbortRecord` lines 240–242, `recordAbort` lines 243–245, S06 lines 281–283 and S15 line 301. This affects C-Records, S06/S15 and the meaning of reconciliation in L04.

The original producer correctly requires terminal local ABORT knowledge before issuing an absence record. The final assertions validate record shape/binding but do not independently assert that a reconciled ABORT has no active hold. A regression in this producer guard can therefore escape the advertised safety conjunction.

**Observed discriminator:** remove only `localKnown == 3` from the copied absence-record producer. Capture two empty-leg records before preparation, then prepare both holds, record ABORT, deliver its authentic proof and book reconciliation using the old absence records. At that point `booked == 1`, `holdA == 1`, `holdB == 1`, while `safe` and CDecision remain true. A separately written `booked ABORT => neither hold is active` invariant produces a native counterexample on the same guided path. The original producer rejects premature capture, which is retained as a positive control. See [the native independent-oracle trace](evidence/observations/runs/abort-guided-abortedBookingResolved/native.itf.json).

**Required repair:** assert the semantic outcome independently of record existence, including no remaining active obligation and justified refunded/absent dispositions. Preserve the producer guard and terminal knowledge. Add stale/premature absence-record controls, valid no-hold ABORT and actual refund positives; check that terminal absence prevents later preparation. Rerun directly affected record safety/progress and relevant recovery configurations after any semantic repair.

### QA-04 — Exact payout recipient is outside the economic state (high)

Location: [dvp.qnt](../../models/dvp.qnt#L45), `receivedA/B` line 45, payout updates lines 167–168, 187 and 195; S05 lines 279–280 and S08 lines 285–289. This concerns task v2 S05 line 68 and recipient-bound backing in S08 line 71.

Descriptors bind recipient IDs and proof substitution is partially exercised. Economic receipt maps, however, are indexed by trade ID and contain only quantity. They do not record the actual credited `(chain, asset, account)` or a transfer receipt with a credited recipient. S05 proves counts and quantities per trade. It cannot observe a correct amount credited to the wrong account on that trade, because that difference has no representation at the payout boundary.

This is a static observability/abstraction gap, not a native counterexample or a claim that the unchanged transition pays a wrong recipient. Correct recipient execution is currently implicit in interpreting the trade-indexed counter. That abstraction needs either an explicit checked relation to account-level effects or a weaker claim; the original exact-recipient requirement must remain visible until discharged.

**Required repair:** represent credited account and asset identity at the economic boundary, preferably account balances or explicit immutable transfer/refund receipts. Check the exact descriptor recipient/quantity with an independent pre/post oracle. Add a mutant that pays another valid account while preserving total supply, one application and the correct amount, plus a wrong-asset control. Revalidate financial safety/mapping and affected topology/escrow paths; preserve original graphs as historical proofs of their original abstraction.
